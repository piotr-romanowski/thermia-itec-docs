# Thermia iTec Eco — RS485 / Modbus protocol and register behaviour

Concise, implementation-oriented reference for the Thermia iTec Eco (controller **CM930**, software
2.3.0–2.4.3; reference unit: Eco 8, version `230`, product code `4`). Goal: enough to build an independent
client (including LLM-assisted) **from this document plus the register reference** — not just a list of
addresses, but how values are encoded, how you read, how you write, and how the online-gateway session
and the pump calendar work.

- **Register map (full):** [`REGISTERS.md`](REGISTERS.md) — slim per-slave table (name, unit, scale, sign,
  status), generated by `tools/generate_registers.py`. This document covers *behaviour*; that table is the *map*.
- **Status of each fact:** `confirmed` = verified on an Eco 8 (panel as oracle, or cross-checked) · `candidate`
  = observed, not fully verified · `unknown` = seen, meaning open. Treat `candidate`/`unknown` as hypotheses.
- **Safety:** every write and every emulated response is **active TX on a live heat-pump bus**. Never run two
  responders on the same accessory slot. Writes change a real pump; keep ranges narrow and verify on the panel.

---

## 1. Physical layer and framing

- **RS485**, half-duplex, **9600 baud, 8 data bits, EVEN parity, 1 stop bit** (9600 8E1).
- **Modbus RTU** framing: `addr | fc | payload | CRC16` (Modbus CRC, poly `0xA001`, little-endian on the wire).
- One master (the display/controller) polls a fixed set of slave addresses in a repeating macro-cycle of
  **32 frames ≈ 4 s** (each slot polled once per cycle, i.e. about every 4 s).
- Frames can exceed 64 bytes (full pages). A stream reframer must wait for the announced length, not cut at 64 B.

### Connector (RJ45 on the indoor I/O card)

Two RJ45 bus ports: **122 = "Display"** (cable to the display, the bus master) and **123 = "Ext."** (external
bus; the Thermia Connect gateway goes here). Connect your own interface to **123**, never in place of the display cable.

Wiring as used on an Eco 8 (listening and transmitting), given by **wire colour** of a standard patch cord:

| Wire colours | Pins (T568B cord) | Signal |
|---|---|---|
| orange + white/orange | 1 + 2 | +12 V supply — leave unconnected unless you power a gateway from it |
| white/green + blue | 3 + 4 | GND |
| white/blue + green | 5 + 6 | B |
| white/brown + brown | 7 + 8 | A |

- Community write-ups (from a breakout cable without numbers) give the same pinout counted from the other end of
  the plug: 1+2 = A, 3+4 = B, 5+6 = GND, 7+8 = +12 V. **Go by colours, not pin numbers**: combining that numbering
  with standard pin-1 orientation puts A on +12 V, which overheats the 120 Ω terminator of a MAX485 module.
- The pins are shorted in pairs inside the pump (doubled lines; continuity check with the pump off), so the port
  carries only **4 lines**: +12 V, GND, A, B. A continuity check is the quickest way to identify the pairs on any cable.
- Connect GND as well as A/B. Before connecting a module, measure with the pump on and nothing attached:
  orange ≈ 12 V against blue, white/green ≈ 0 V, A and B only a few volts.
- Other iTec models (e.g. XT10) are expected to match but are not verified here.

### Slaves

| Addr | Role | FC used | Notes |
|---|---|---|---|
| `0x02` | Indoor board | `0x17` (read/write), `0x03` | operating data |

Function codes seen: `0x03` (read holding), `0x04` (read input), `0x10` (write multiple), `0x17`
(read/write multiple — the display's combined poll), `0x90` (exception).

## 2. Value encoding

Every mapped register carries a `scale`, and some carry a `signed` marker. Decode as:

1. **Scale:** `value = raw × scale`. Temperatures are usually `×1` or `×0.1 °C` (per register — read the map,
   do not assume). A **negative scale** is used where the panel shows the negated register (e.g. heating
   `START`/`STOP` degree-minutes: panel value = `−5 × register`; aux-heater `START`: panel = `−15 × register`).
2. **Sign:** some words are **two's-complement signed**. Two cases:
   - whole-word signed (e.g. heating-curve offsets `±5`): interpret the 16-bit word as `int16`.
   - **low-byte signed** (e.g. outdoor temperature): only the low 8 bits are the signed value — sign-extend
     from bit 7, ignore the high byte. A naïve read of the full word shows `255` instead of `−1`.
3. **Enums:** small integers with named states (e.g. operation mode, §11).
4. **Bitfields:** a word whose bits are independent flags (e.g. operation-status `2149`, alarm words, §10).

### Address convention

- Keys in the map: `R<slave> reg<n>` (read) and `W<slave> reg<n>` (write).
- On the **`0x0F`** session the **bus page address (hex) equals the Connect/panel parameter number (decimal)**:
  `1000 = 0x03E8`, `1012 = 0x03F4`, `1363 = 0x0553`, `2149 = 0x0865`. A page is a contiguous block of words
  starting at such an address; a parameter lives at `page_start + offset`.

---

## 3. Reading

- **Operating data / sensors:** block reads on `0x02` (FC `0x17`/`0x03`) and `0x1E` (FC `0x04`). The outdoor
  block is also readable with `FC03` on demand.
- **Online-session values (`0x0F`):** the controller does **not** push most setting pages unsolicited in a live
  session. You request them through the mailbox (§7) and read them from the pages it then publishes. Alarm words
  (`085F`) come only on change or on explicit request (§7.4).

---

## 4. Writing — overview

Two independent paths, depending on which slot you emulate:

- **Path A — room-sensor slot `0x0A`** (§5): inject a measured room temperature, a setpoint request, or a DHW
  top-up request. Simple, always available, limited to those few fields.
- **Path B — online-gateway session `0x0F`** (§6–§9): full access to every Connect setting page, the calendar,
  and the alarm words — but requires joining the gateway session (challenge/approval).

Never enable both responders for the same slot at once, and never a second `0x0F` responder beside a real one.

---

## 5. Path A — room-sensor emulation (`0x0A`)

The display polls `0x0A` with **FC `0x17`**: the write part carries `[outdoor, room setpoint, …]`, the read part
asks for **3 registers** the sensor answers. Response frame: `0A 17 06 <reg0> <reg1> <reg2> CRC` (11 bytes).

| Reg | Meaning | Encoding |
|---|---|---|
| `reg0` | room temperature | `×10 °C` (e.g. `215` = 21.5 °C); `0` is treated as “no reading” |
| `reg1` | room **setpoint request** | `°C` (10..30), `0` = none (genuine sensor behaviour) |
| `reg2` | status / **DHW top-up** request | `0` = none; non-zero = status / top-up |

Also observed: the display pushes `W10 46022` = status to the sensor (`0` ok / `1` alarm / `2` top-up).

**Delivery check:** the controller republishes the room temperature it actually received in the `0x0F` runtime
word **`2060`** (`×10 °C`, page published about every 21 s). It followed the emulated `reg0` change for change
(6/6 over one night, 5–15 s later) — use it to confirm the emulation arrives, not just that it was sent. confirmed.

**Foreign-responder guard:** if a `0x0A` response appears that you did not send, another device owns the slot —
latch and stop transmitting until cleared by hand. (Most transceivers don't echo your own TX; if yours does,
tell the responder so it treats the next identical frame as its own echo, not a foreign responder.)

---

## 6. Path B — online-gateway session (`0x0F`): lifecycle

Layers, in order:

1. **Challenge / approval.** The controller opens a session by sending a 16-byte challenge on `0x0F`
   (`FC23`, handshake windows `@071C` / `@0730`). A gateway answers with a 16-byte response within ~30–60 ms,
   and the controller then starts its configuration export. The controller **verifies** the answer
   (a recorded reply is refused). **The response algorithm and key are NOT part of this documentation or the
   reference client** — they are supplied by an external function (`approval(challenge[16]) -> response[16]`).
   Without it, a client can only **join an already-live session**, not initiate one after a pump restart.
2. **Page publications.** After approval the controller publishes pages as **`FC16`** writes
   (`0F 10 <page> <count> <bytes> <words…> CRC`). The gateway **echo-ACKs** each in-scope page (sends the 6-byte
   header back). Bootstrap = 32 pages `03E8..06F4`; runtime = `07D0..0884`; alarms = `085F`.
3. **Mailbox.** The controller periodically reads the gateway's **mailbox** with **`FC03 @0708`, 6 words**
   (`W0..W5`). The words carry *request bits*: the gateway sets them to ask the controller to (re)publish pages
   or to push a modified page back (§7).

Foreign-gateway guard: a `0x0F` response that is not ours means a real gateway is present → go silent until
restart. Never answer `0x0F` while the genuine module is connected.

---

## 7. Mailbox `0708` (W0..W5) and the request bits

The mailbox is 6 words. Pages are addressed by **bit index** = position in the 32-entry bootstrap list
(`03E8`=0, `03FC`=1, …). Words split that index into read vs push, low vs high half:

| Word | Purpose | Bit → page |
|---|---|---|
| `W0` | **push** (desired-page write) request, pages 16..30 | bit `i-16` |
| `W1` | **push** (desired-page write) request, pages 0..15 | bit `i` |
| `W2` | **read** request, pages 16..30 | bit `i-16` |
| `W3` | **read** request, pages 0..15 | bit `i` (bit0 = `03E8`) |
| `W4` | runtime-page requests + **alarm** | bit `7` (`0x0080`) = alarm page `085F` |
| `W5` | flags | `0x0006` holds the online icon; `0x0007` in a full dump |

When the controller publishes a requested page, the matching request bit is cleared (mapping derived from a
genuine capture, e.g. `03E8`→W3.0, `07D0`→W4.0, `0864`→W4.8).

### 7.1 Desired-page write (a setting)

To change a setting at address `A` (page `P`, offset `o`):

1. Make sure you hold the current image of page `P` (request a **read** of `P` if you don't — bit in `W3`/`W2`).
2. Put the modified word into your copy of page `P` and raise the **push** bit for `P` (in `W1`/`W0`).
3. The controller pulls your page image and republishes `P`. **Confirmation = it republishes the identical page.**
4. **`one_shot` commands** (e.g. DHW boost `1072`) are *commands, not settings*: after accepting, the controller
   publishes the page with that word back at **0** (and the page shape/length may differ). Treat “own word back
   at 0” as accepted, not as a mismatch.

Writes are gated by a **whitelist with ranges** (§9). Timeouts: write 20 s, refresh 10 s.

### 7.2 READ_ALL (current pages)

`W2=0x0001 + W3=0x0019` → the 4 live pages `03E8`, `042E`, `0442`, `0546`. Cheap periodic refresh of the pages
the panel does not push on its own (mode / DHW / curve). Do this every few minutes.

### 7.3 Full resync (all 31 pages)

Two forms:
- **FULL_SYNC** (one shot): `W3=0xFFFF + W2=0x7FFF` (31 page bits) **plus** `W4=0x0080` and `W5=0x0007`. The
  genuine dump; ~31 s, and it **pauses the `0708` polling** (caused by the 31 page bits, not the `0x0080`).
- **SYNC_PAGED** (recommended): the same 31 pages in **chunks of ≤4 bits** per mailbox cycle — 31/31 in ~30–40 s
  **without** stopping the `0708` polling. Use this to avoid dropping the panel's online icon.

### 7.4 Alarm words `085F`

In a **live** session the controller publishes the alarm page `085F` (words `2143..2147`) **only on a change**,
or on explicit request via **`W4` bit `0x0080` alone** (no page bits). It is *not* carried by READ_ALL, single
page bits, or SYNC_PAGED. Request it once after joining and then on a timer (e.g. every 15 min) to keep the
alarm words fresh. (This differs from a pump with **no** gateway, where `085F` streams every ~2 s.)

---

## 8. Never two responders

On `0x0A` and on `0x0F` there must be exactly one responder on the bus. A second one corrupts the session and
can raise a controller alarm (e.g. `44` gateway-link, or `COM.ERR.ONL./LINK`). Both responders here latch off
the moment they hear a foreign reply on their slot.

## 10. Status and alarm bitfields

- **`2149` (`0865`) operation_status** — read-only runtime bitfield (page `0864`):
  b0 heat-building · b1 hot-water · **b2 hot-water top-up** · b3 heat-pool · b4 defrost-building ·
  b5 defrost-hot-water · b6 outdoor-stop · b7 cooling · b9 concrete-drying.
- **Alarm words `2143..2147` (page `085F`)** — non-zero = active alarm; bit names per the Connect 2.3.x alarm
  definitions. `2145` also carries the `0x06` transport ACK (bit 11 = internet-gateway comm error). “No alarm”
  is only trustworthy once `085F` has been read this session (§7.4); otherwise unknown.
- **Outdoor unit (`0x1E`):** `R30 reg20` = operating-state enum, `R30 reg21` = status bitfield
  (e.g. `0x40` DHW context, `0x20` heating context, `0x200` outdoor-unit active; `@20` b1 reverse cycle,
  `@21` b2 defrost). `W2 43020` b0 = DHW request, b6 = heating context.
- **SG-Ready:** `R2 43005` = ±1000 (SG2 off/on), `R2 43011` = SG1 (value conflict open).
- **Calendar function in effect `1467` / `1565` / `1663` / `1761`** (`05BB` / `061D` / `067F` / `06E1`) — one word
  per calendar function, set by the controller: `1` while F1 DHW block / F2 EVU / F3 silent mode / F4 temperature
  reduction is in effect, `0` otherwise (§12). confirmed.
- **Operating counters `2160..2168` (page `0870`)** count **whole hours** (e.g. aux heater 1 `2167` stepped
  206→207 after ~0.7 h of relay time spread over ~65 short switch-ons, so sub-hour runs accumulate internally and
  only the integer is published). Do not derive daily heater use from them; use the heater bits
  (`W2 43020` b7, `43021` b4). confirmed (10 days, 2 steps).

### 10.1 Heating regulation as seen on the bus (Eco 8, passive overnight capture, 13 compressor starts/stops)

- **Heat demand `2120`** (panel shows `−2120`) is a degree-minute integral of *wanted − actual supply*. The compressor
  **starts when `2120` reaches +50** (panel −50 = HEATING START `1073` × −5) and **stops at −50** (panel +50 = HEATING
  STOP `1074` × −5) — 7/7 starts, 6/6 stops. After a stop the value jumps to about −5, then 0, and rises again
  (≈ 1 unit per 20 s while supply is ~2 K below wanted). confirmed.
- **Start/stop sequence:** `2150` bit0 (heating demand queued) is set ~40 s before the compressor starts and clears at
  the start; the circulation pump (`2094` bit3) starts ~40 s before the compressor and runs ~1 min after the stop;
  the outdoor fan (`2094` bit2) starts with the compressor and stops ~1 min after it (14/14 cycles). confirmed.
- **`2095`** mirrors `R30 reg21` with ~15 s delay. **`2117`** bit9 follows the outdoor-unit run request (`R30 reg21`
  bit9, a few s later); bit8 is set in heating context, clear during DHW (`512` DHW, `768` heating, `0` idle). candidate.
- **Cycling at the curve minimum:** when the wanted supply sits at the curve MIN and the compressor's lowest output
  (15–16 Hz) overshoots it by 1–2 K, the integral drains to −50 and the unit cycles — one night showed a very regular
  ~45 min on / ~20 min off (6 cycles, ±1 min). This follows from the minimum output, not a fault.
- **HOT WATER TIME / HEATING TIME** (`1054` / `1076`, 30 min) are alternation limits that apply only when DHW and heating
  are demanded at the same time (Danfoss DHP-iQ Operating Guide wording, same menu on the iTec Eco); without a heating
  demand a DHW cycle simply runs to its stop temperature. candidate (not yet observed hitting the limit).

## 12. Pump calendar (`0x0F` pages `055A..06E5`)

Read-only from the controller (published during bootstrap / full sync and after a panel edit); written back via
the desired-page mechanism.

- **Layout:** `055A..06E5` = 396 words = **4 functions × 98 words**. Each function = **8 records × 12 words** +
  a **slot bitmap** (bit `n` = slot `n` active) + a **status word** (function in effect, below); 4-word tail
  `06E2..06E5` (meaning unknown; `06E2` changes on its own, e.g. bit 1/bit 2 during the day).
- **Record (12 words):** `mode, start[min,hour,day,month,year−2000], stop[min,hour,day,month,year−2000], weekday_mask`.
- **Functions:** `F1` DHW blocked · `F2` EVU (stops the pump) · `F3` silent mode · `F4` temperature reduction.
- **Modes:** `0` = date range (weekday mask 0, evaluated against the clock) · `1` = **weekly** (weekday mask:
  bit0 Monday … bit6 Sunday; date words ignored by the panel).
- **Add / delete:** write the record content into a slot; delete = write the **empty record**
  (`{0,0,0,31,12,0, 0,0,31,12,0,0}`). One record spans 1–2 page writes; a failed step drops the rest.

**Operational behaviour (Eco 8) — not just addresses.** The controller recomputes each function's slot bitmap
from record content on every calendar write (`bit_i = slot i content ≠ empty record`); you never write the bitmap
yourself. Three consequences that matter in practice:

- **Slots are released only from the top.** The bitmap covers slots `0..highest non-empty`: deleting the
  *highest* real entry also releases every empty slot below it (a "cascade"), but deleting an entry **below** an
  occupied slot leaves that slot in use with empty content (a hole) until something is written into it. To change
  an entry, **overwrite its slot in place** (write the new record to the same slot) instead of delete + add.
  (Corrected 2026-11-17, LIVE: an earlier reading "every empty slot is dropped" was wrong.)
- **A no-op write does nothing.** Writing the empty record to a slot that already holds exactly the empty record
  changes no bytes, so nothing is transmitted and nothing recomputes. A slot stranded as the exact empty record
  (a "year-2000 phantom" — e.g. from an earlier interrupted delete) **cannot be removed on its own**; it clears via
  the cascade above, or by being overwritten with a new entry.
- **Reuse on add.** Pick the lowest slot whose *content* is empty (not the lowest clear bitmap bit). This fills a
  hole/phantom instead of leaving an empty slot below a fresh entry, and keeps entries packed from slot 0.
- **Edit in place** (verified LIVE 2026-11-17): writing a record to an in-use slot (including an empty-content hole)
  replaces it; nothing else moves.

(On XTR the slot bitmap is an independent validity flag, so none of the above applies there.)

**No entry over midnight (verified LIVE on Eco 8, 2026-11-17).** A weekly entry with start > stop (e.g.
`22:00→08:00`) is accepted and shown by the panel, but the controller **never runs it**. Two nights showed no
setback, while a same-day weekly test entry (`10:00–11:00`) and a date-range entry took effect to the minute. This
matches the iTec Eco User Guide (AWIE01UG102, p.19): *STOP no later than 23:59, START no earlier than 00:01;
overnight = two entries.* So write a night setback as **`start–23:59` + `00:01–stop`** with the same weekday mask.
First night with such a pair (2026-11-17→18): both entries ran; in the two-minute gap the controller really
returned to the day setpoint (circuit-1 wanted temperature rose by 6 °C for two minutes), harmless.

**Function in effect — status word (verified LIVE on Eco 8, 2026-11-18).** The word after each function's bitmap
(offset 97 of the block: `05BB` F1, `061D` F2, `067F` F3, `06E1` F4) is written by the controller itself:
`1` while that function is in effect, `0` otherwise. The controller publishes the page holding it (`059C`, `05FF`,
`0662`, `06C5`) **only at a transition** (twice, ~30 s apart), so a passive listener sees every start and stop.
Evidence: F4 over one night (all three transitions of a two-entry setback; page `06C5` never published in
between over 9 h);
F1/F2/F3 with three 5-minute date entries (each 0 → 1 at start, 1 → 0 at stop; EVU stopped the compressor).
Use this instead of evaluating the entries against the clock. Note: the panel's *effective* room setpoint during a
setback (it shows the reduction temperature) is not on the bus — only the two settings `1007` / `1012`; combine
`1761` with them. Transitions land ~20 s after the minute when the controller clock lags.

## 13. Integrity notes

- **Excluded on purpose:** the `0x0F` approval **algorithm and key**, and the source/provenance of that
  discovery. A reference client exposes only the hook interface; each user supplies their own `approval()`.
- Mark every claim `confirmed` / `candidate` / `unknown`; do not promote a hypothesis by omission.
- This documentation is model-specific to **CM930 2.3–2.4 / Eco 8**. Other iTec models (XTR, ATEC) share the
  Connect profile but differ in topology, index collisions, and which writes a given controller accepts.

### 13.1 Legacy slot `0x06` and controller timing (parked research)

- **Transport (confirmed, also on an XTR M):** any syntactically valid 12-register reply on `0x06` makes the display
  poll it at an alternating 0.7 / 1.4 s instead of ~4.3 s; the fast cadence lasts ~2 min after the replies stop.
  Reply word `@45002` (`0xAFCA`) = `0x03E8` makes the display write 16 to `0x0F @2145` (ACK); 0 clears it. `0x03E8`
  is a constant (1001, 1002, 999, 1234 give no ACK). The ACK is transport only — no payload tried (zeros, status
  words, product id, ASCII, echo, RTC, setpoints) makes the module appear as an application-level module.
- **Version row (confirmed):** with valid replies the VERSION page shows an `EXP` row = reply word `@45009`
  (`0xAFD1`) / 10; it disappears ~2 min 15 s after the replies stop. Metadata only.
- **Heartbeat `@45020` (confirmed):** a copy of `0x02 @43022` bit 5 (heating allowed: displayed outdoor
  temperature below the heat-stop setting, hysteresis 2–3 K), pulsed 0 ↔ 32 (15–20 s high, period ~64 s).
  Any non-zero `@45002` changes the pulse value to 16.
- **Controller "minute" ≈ 63.9 s (candidate):** mean heartbeat period 63.87 s over 7300 periods. In those units a
  periodic routine (a 62–68 s state in `@43020`, then a 10-minute window in `@43022`) repeats every 1440 minutes
  = 25 h 33 min real time — a prediction from this was met within 117 s a day later; probably the daily
  circulation-pump exercise. Hot water / heating alternation when both are demanded measures 1916–1922 s
  (= 30 such minutes).
- A full address scan (1–247, FC03/FC04) found no hidden slave. The gateway session of current pumps lives on
  `0x0F` (§6), not here.

## 14. Frame layouts and page map (reference)

Everything a full `0x0F` client needs beyond §1–§13. All multi-byte fields are big-endian on the wire;
append a Modbus CRC16 (poly `0xA001`) to every frame.

### 14.1 Frame layouts

**FC03 — read holding (mailbox / block reads)**
```
request :  addr 03 <start(2)> <qty(2)> CRC
response:  addr 03 <bytecount(1)=2*qty> <qty words> CRC
```
Mailbox read: `0F 03 0708 0006 CRC` → `0F 03 0C <W0..W5> CRC`.

**FC04 — read input (outdoor `0x1E` sensor block):** same shape as FC03 with fc `04`.

**FC16 — write multiple (the controller publishes a page; you push a desired page)**
```
0F 10 <start(2)> <count(2)> <bytecount(1)=2*count> <count words> CRC
```
Echo-ACK a published page by reflecting its first 6 bytes (`addr fc start count`) + CRC — no data.

**FC23 (`0x17`) — read/write multiple.** Used for the `0x0F` challenge and the `0x0A` poll.
```
request :  addr 17 <r_start(2)> <r_qty(2)> <w_start(2)> <w_qty(2)> <w_bytecount(1)> <w_data...> CRC
response:  addr 17 <r_bytecount(1)=2*r_qty> <r_qty words> CRC
```
The 16-byte write payload (challenge) begins at **byte offset 11** of the request
(`1 addr + 1 fc + 2 + 2 + 2 + 2 + 1 = 11`).

- **`0x0F` challenge:** `0F 17 | r=0730 qty=0008 | w=071C qty=0008 | bc=10 | <16 challenge bytes> | CRC`.
  Gateway answer: `0F 17 10 <16 response bytes> CRC` (the response algorithm is **not** in this doc — §13).
- **`0x0A` poll:** the display's write payload holds `[?, outdoor, setpoint_hi, setpoint_lo, …]` — **outdoor** is
  the signed low byte of write-word 1, **setpoint** is write-word 2 (`int16`). The sensor answers 3 words:
  `0A 17 06 <reg0(2)> <reg1(2)> <reg2(2)> CRC` (reg0 room temp ×10, reg1 setpoint request, reg2 status; §5).

### 14.2 Page map

Pages are addressed by **index = position in the bootstrap list below**. Mailbox request bits (§7): for page
index `i` (0..30), the **read** bit is `W3` bit `i` if `i<16` else `W2` bit `i-16`; the **push** bit is `W1`/`W0`
the same way. Each published FC16 frame carries its own `start` and `count`, so you decode a publication
directly (`parameter = start + offset`, value via `REGISTERS.md`) without this list — you only need the list to
*request* a specific page.

**Bootstrap pages (32; indices 0–31, only 0–30 are individually request-able):**
```
 0 03E8   1 03FC   2 0410   3 042E   4 0442   5 0456   6 046A   7 047E
 8 0492   9 04A6  10 04BA  11 04D8  12 04F6  13 050A  14 051E  15 0532
16 0546  17 055A  18 057B  19 059C  20 05BD  21 05DE  22 05FF  23 0620
24 0641  25 0662  26 0683  27 06A4  28 06C5  29 06EA  30 06F1  31 06F4
```
`055A..06E5` (indices 17–28) is the calendar block (§12). `06EA` (index 29) is the clock page (§14.3).

**Runtime pages (10):** `07D0 07E4 07F8 080C 0820 0834 0848 0864 0870 0884`. Requested/cleared via `W4` bits —
`07D0`→b0, `07E4`→b1, `07F8`→b2, `080C`→b3, `0820`→b4, `0848`→b6, `0864`→b8 (holds `2149` operation-status),
`0870`→b9. (`0834` is ACK-required but not a request bit.)

**Alarm page:** `085F` — request via `W4` b7 (`0x0080`) only (§7.4).

**READ_ALL** (`W2=0x0001 + W3=0x0019`) = indices 0 (`03E8`), 3 (`042E`), 4 (`0442`) + `W2` b0 = index 16 (`0546`).

### 14.3 Clock page `06EA`

7 words, local time: `[sec, min, hour, day, month, year−2000, weekday]`, weekday `0 = Monday`. Written with the
desired-page mechanism; the whitelist entry carries no range (the image comes from the client's clock).
